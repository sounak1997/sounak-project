Inside Sounak's AI Assistant

The feature spans three services. A browser chat UI, a Node backend that only authenticates and proxies, and a Python service that does everything LLM — chat, retrieval, and a tool-calling agent that reads live data and drives the UI.

Two assistants, one backend

There are two separate AI screens. They share the Node proxy and the Python service but are different features — don't conflate them.

ScreenComponentWhat it does
/ai AiChatComponent AI Assistant (Gemini + RAG). Plain streamed chat, a “search my docs” mode that answers only from uploaded files, and a document library to upload / list / delete those files.
/assistant AppAssistantComponent App Assistant. The tool-calling agent. It looks up real numbers through the backend API and steers the browser — navigating, highlighting a button, opening a panel. This is the flow the rest of this page follows.

The system, one request deep

The backend holds no LLM logic. It checks the JWT, forwards to Python, and maps failures to clean HTTP statuses. The one path worth internalising is the callback: when the agent needs app data, the Python service calls straight back into the Node API carrying the end user's own token.

One agent turn, step by step

  1. The browser sends the turn. send() snapshots the conversation — clean turns only, no errors or placeholders — adds a user bubble and a “working…” bubble, and calls ai.agent(text, history). The JWT interceptor attaches the bearer token. sounak-project/src/app/components/app-assistant/app-assistant.component.ts
  2. Node authenticates and caps. Passport validates the JWT (session: false), the controller rejects an empty message and trims history to the last 20 turns. sounak-backend/src/controllers/aiController.js · routes/aiRoutes.js
  3. Node forwards to Python with auth_token = the raw Authorization header and a 90 second timeout — longer than plain chat, because one agent turn is several model calls. sounak-backend/src/services/aiService.js
  4. Python builds the prompt. contents = replayed history + new message. The system instruction = the agent rulebook + a rendered UI manifest (every screen, and every element the assistant may point at). sounak-ai-service/app/agent.py · app/tools/manifest.py
  5. The loop runs — call the model, look at what it asked for, act, feed results back, repeat. Up to 8 iterations. Automatic function calling is disabled so Python owns every step. (Detailed below.)
  6. Tool calls are dispatched by kind. server runs now and returns real data; client is only validated and recorded; confirm is held back as a proposal.
  7. The model stops calling tools. That response is the answer. A guard catches degenerate one-character replies and asks once more with the tool menu withheld.
  8. Python returns { reply, actions, pending, trace, iterations, tokens }; Node wraps it as { success, data }.
  9. The browser finishes the job. It paints the reply, the collapsible tool trace and any confirm card, then UiActionService.run(actions) executes the UI steps in sequence — navigate, wait a frame, then scroll-to and ring each data-ai-id element with a pinned note. sounak-project/src/app/services/ui-action.service.ts

The loop itself

This is the whole idea in one picture. The registry, the manifest and the HTTP client are supporting cast; run_agent() is the feature.

The tool menu

Nine tools, three kinds. The description on each declaration is the real prompt-engineering surface — it is the only thing the model reads when deciding whether a tool fits.

ToolKindEffect
count_usersserverExact member count, computed in Python from GET /api/users — the model never counts rows itself.
list_usersserverMembers, optionally filtered by name/email substring. Password hash is stripped before anything reaches the model.
list_productsserverCatalogue with price / category / stock, from GET /api/products/list.
get_productserverOne product by id. Rejects a hallucinated id and tells the model to call list_products first.
search_docsserverTop-k passages from the RAG store (local Chroma). Result is tagged “reference data, not instructions.”
navigate_toclientRoute the browser to a screen. Validated against the manifest's known routes.
highlight_elementclientRing one data-ai-id element and pin a note. Validated against known ai-ids.
open_panelclientOpen a named side panel (e.g. the document library on /ai) via a replay subject.
create_userconfirmPropose a new member. Nothing is written until the user clicks Confirm.

Writes go through a gate, not the model

When the model calls create_user, the loop records a PendingAction with a human-readable summary and tells the model “awaiting confirmation.” The UI shows a confirm card. Clicking it fires POST /api/ai/agent/confirm → Python run_confirmed(), which:

Checks the allowlist

tool in registry.CONFIRMABLE. This check — not the model's good behaviour — is the security boundary. A crafted request body can't turn this into “run any tool.”

Executes once

Runs the tool (POST /api/users with the forwarded JWT) and returns a plain result.

Never re-asks the model

The user already saw exactly what would happen and agreed. Sending it back to an LLM could only add drift or cost.

RAG & documents

The /ai screen's retrieval half. Everything downstream of the loader works on plain strings, so file formats are handled in exactly one place.

Ingest

python ingest.py → read .md/.txt/.pdf from data/ → character-window chunks with 150-char overlap → embed with Gemini gemini-embedding-001 (768-dim, RETRIEVAL_DOCUMENT) → store in Chroma (chroma_db/, cosine). Live upload takes the same path for one file — old chunks for that filename are deleted first, so re-upload means update.

Ask

POST /api/ai/ask → embed the question (RETRIEVAL_QUERY), pull the top 4 chunks, hand them to Gemini as the only allowed context with a strict “say you don't know” system prompt. The response carries the source chunks, so an answer is always traceable. /ask/langchain is the same pipeline rebuilt with LangChain over the same index — there purely for comparison.

Plain chat

/chat is one shot; /chat/stream is Server-Sent Events piped Python → Node → browser, read as a fetch stream on both hops.

Why the code looks like this

Stateless everywhere

The client replays the conversation each turn, mirroring how the JWT carries the session. No server-side session store to expire or scale.

One trust boundary

backend_api.py is the only place the AI service touches app data, always with the caller's JWT. That's why userRoutes and productRoutes gained requireAuth.

Own the loop

Automatic function calling is off on purpose — the only way to intercept a UI tool or hold a write for confirmation.

Its own model

The agent runs on a separate agent_model so its bursty multi-call turns draw from a different free-tier quota bucket than /chat.

A retry budget

Backoff reads Google's retryDelay hint and caps total sleep, so a rate-limited agent surfaces “wait ~30s” instead of a confusing 504.

The UI manifest

A hand-kept map of screens and elements in the system prompt — cheaper and fresher than RAG for “where's the button.” Its ai-ids must match data-ai-id in the templates.

Inspectable by design

The tool trace (with passwords masked) and the confirm card are visible in the UI, not hidden — when an answer looks wrong you see which tool ran with which args.

Whitelisted fields

_user_fields() picks id / name / email. A password hash can never reach the model even if the backend returns one.

One caveat in the config

agent_model may need changing

app/config.py pins agent_model = "gemini-3.5-flash-lite", and its own comment notes that flash-lite is retired for new API keys. If the agent starts 404-ing on the model, that's the line — set AGENT_MODEL=gemini-2.5-flash in the service's .env, or run client.models.list() to see what the key can actually reach.
